1. FINAL AUTOMATIC-RESTART DESIGN (as approved by the owner)
============================================================
The owner explicitly chose a LIMITED user-account Task Scheduler task with
crash-recovering supervision at interactive login, NOT an SCM Windows service
and NOT LocalSystem. Consequence, stated honestly: the stack starts when the
the operator account logs in, not before first login; it does not run in the boot
session. If a boot-before-login service is ever required, the owner must pick
a service account and re-approve; that is a separate change.

do not reuse this machine's XML verbatim.

2. SUPERVISOR: THREE OWNED SERVICES + PROCESS-TREE CONTAINMENT
==============================================================
scripts/windows/supervise.pyw runs scripts/windows/project_supervisor.py, which
owns exactly three children:
  0 satellite_gateway.loop            .venv/Scripts/python.exe      ports 8765,10702
  1 hermes_gateway.pairing_server     .tools-venv/...               port 10704 (dials 10702)
  2 hermes_cli.main gateway run       HERMES_HOME/hermes-agent/venv python, cwd hermes-agent, port 8642
Matching for the gateway is strict: only '-m hermes_cli.main gateway run'; it
does NOT adopt/kill desktop serve, chat, or the Hermes Desktop app's own
embedded backend. Foreign processes and pre-existing listeners are never
adopted or killed.

Crash containment: scripts/windows/windows_job.py puts every owned child tree in
a private Job Object with JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE. Children are
created CREATE_SUSPENDED, assigned to the job, then resumed via NtResumeProcess
(ntdll), so nothing can run (including the venv redirector's child interpreter)
before containment. Assignment failure kills only the just-launched suspended
child and fails closed. If the supervisor itself dies, Windows kills the whole
owned tree - no orphans. Verified by native smoke test (abrupt owner death
killed redirector, interpreter and descendant).

Child environment hygiene: inherited PYTHONPATH, PYTHONHOME, VIRTUAL_ENV removed;
PYTHONNOUSERSITE=1; HERMES_HOME defaults to the profile; PYTHONUNBUFFERED=1.
Logs: logs/windows/supervisor.log + one rotating child log per module.
Restart policy: exponential backoff 10s doubling capped 300s, reset after 300s
stable; single-instance OS byte lock on state/windows-supervisor.lock
(auto-released on hard crash, no stale-PID logic).
Planned stop sentinel: create state/windows-supervisor.stop; the supervisor
exits and its job object terminates only owned children. Leaving the sentinel
in place intentionally prevents future starts.

3. MIGRATION FROM THE OLD TWO-VBS LOGIN STARTUP
===============================================
Old mechanism (superseded, now archived): Startup-folder VBS launchers
HermesVoiceSatelliteProject.vbs and Hermes_Gateway.vbs plus a manually started
two-service supervisor. Both VBS files were MOVED (not deleted) to
<project>/backups/login-launchers-before-task/. The old supervisor tree was

and an explicit guard refused the Hermes Desktop process chain.
scripts/windows/activate_task_migration.ps1 captures that guarded sequence.
