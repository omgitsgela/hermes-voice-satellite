5. ESP32 BACKUP, REGION FLASHING AND READBACK
===========================================
Hardware actions below require separate operator approval and the user's board.
Use the ESP32 USB serial/JTAG connector, NOT the audio chip USB-C socket. Identify
the COM port anew; examples use COM<PORT>. Close serial monitors first. Use a data
cable and stable power. Do not open COM ports during documentation-only work.

Before any change, capture the full fitted 8 MB flash to a NEW private file:
  .tools-venv/Scripts/python.exe -m esptool --chip esp32s3 --port 'COM<PORT>' --baud 460800 read-flash 0 8388608 '<PRIVATE_NEW_BACKUP.bin>'
Hash it and retain it privately. A provisioned dump includes Wi-Fi credentials,
private keys and device state; do not put it on the documentation NAS. A hash is
safe to record, but the bytes are not. Separate stock images from personal dumps.

IMPORTANT: the bundler pads gaps with zeroes. Do NOT write its merged bundle
contiguously at 0x0 for normal project updates: that could overwrite NVS/PHY and
other preserved data. Extract reviewed components to a NEW output directory:
  .tools-venv/Scripts/python.exe scripts/bundle-esp32-flash.py --verify '<RELEASE_BUNDLE.bin>' --check '<RELEASE_MANIFEST.txt>' --expected-sha256 2d67d25fb3d648ca79383758ca509d2269eafd5b7bf59c7c43345e953283e436 --extract '<NEW_EXTRACT_DIR>'
Check the manifest/extraction filenames, sizes and per-component hashes. The
actual local build map is 0x0 bootloader, 0x8000 partition table, 0x10000 app;
confirm the selected release manifest agrees before using this example:
  .tools-venv/Scripts/python.exe -m esptool --chip esp32s3 --port 'COM<PORT>' --baud 460800 write-flash --flash-mode dio --flash-size 8MB --flash-freq 80m 0x0 '<EXTRACTED_BOOTLOADER.bin>' 0x8000 '<EXTRACTED_PARTITION_TABLE.bin>' 0x10000 '<EXTRACTED_APPLICATION.bin>'
Read back EACH exact component length from its manifest and compare SHA256 with
the extracted component. Do not treat the writer's own verify message as the only
evidence. Do not run erase-flash. Firmware/table are coupled; do not update one
with an incompatible layout. ESP32 read/write may reset the board.

Selected source partition layout (recheck for a different release):
  NVS       0x009000 size 0x006000   preserve profiles and settings
  PHY       0x00f000 size 0x001000   preserve
  factory   0x010000 size 0x200000   application
  storage   0x210000 size 0x400000   first 8192 bytes reserved for TLS

Do not format storage/model as SPIFFS merely because the partition subtype says
spiffs. A filesystem header would overwrite the credential/model header.

6. SEPARATE AUDIO COPROCESSOR DFU / WINDOWS DRIVER STEPS
======================================================
ESP32 firmware flashing does NOT update the XMOS/XVF3800 coprocessor. Current
project firmware requires v1.0.9 48 kHz MASTER on the audio chip; ESP32 is the
48 kHz I2S SLAVE and decimates to 16 kHz for wake/uplink. Stock v1.0.4 is a
16 kHz slave and is incompatible with this current pairing (dead mic/init_failed).

Physical actions are USER actions; do not infer they happened from a command:
1. Disconnect power. Move the data cable to the audio chip USB-C socket next to
   the 3.5 mm jack, NOT the ESP32 serial connector.
2. Hold Mute while restoring power, keep holding until the red LED blinks, then
   release. This is Safe Mode/DFU. Ask the user to do it; no software substitute.
3. List DFU devices. Expect VID 2886 PID 001a and alt 1, reSpeaker DFU Upgrade.
4. If Windows sees the DFU device but libusb cannot open it, have the user select
   ONLY the corresponding ReSpeaker DFU interface in Zadig and assign WinUSB.
   Review name/VID/PID first. Do not replace the ordinary audio, ESP32 serial,
   keyboard or hub driver; do not click driver/admin prompts without approval.
   A driver change is separate from a firmware write.

Existing local tool paths (not installed by this task):
  <project>/tools/zadig-2.9.exe
  <project>/tools/dfu-util/dfu-util-0.11-win64/dfu-util.exe

From project root, after physical/driver confirmation:
  tools/dfu-util/dfu-util-0.11-win64/dfu-util.exe -l
Verify the image SHA256 in section 5, then (SEPARATE CHIP WRITE):
  tools/dfu-util/dfu-util-0.11-win64/dfu-util.exe -R -e -a 1 -D firmware/stock/xmos-official-v1.0.9-48k-master-dfu.bin
No sudo on native Windows. Invalid DFU suffix signature can be normal for this
raw image; it is NOT by itself proof of failure or success. Look for manifest/
idle completion with status 0, then replug normally and read the ESP32 bring-up
line: version=1.0.9. Transfer completion alone does not prove working microphones.
Do not send ESP32 flash offsets to the coprocessor or use its port for esptool.

13. TROUBLESHOOTING, INCLUDING DELAYED OLD COMPLETIONS
====================================================
Import errors despite a successful install:
  Check which python.exe ran; remove inherited PYTHONPATH/PYTHONHOME/VIRTUAL_ENV
  only from the relevant child environment and use PYTHONNOUSERSITE=1. Do not
  solve this by sharing Hermes site-packages with the SDK/runtime venv.
PermissionError in model flash:
  Check the closed temporary-file fix and focused test; do not disable antivirus
  or make temp directories globally writable as a first response.
AttributeError: os.fchmod:
  Use the guarded native fix; do not strip all atomic-persistence protection.
Pairing issuer cannot find python3:
  Ensure sys.executable in ScriptEnroller and correct interpreter/package imports.
TLS authentication/pinning fails after moving host:
  Compare endpoint, server SAN and pinned certificate, and device identity mapping.
  Reuse trust deliberately; do not regenerate CA, bypass TLS or enable plaintext
  to hide the mismatch. Check local-subnet firewall and the correct LAN address.
DFU sees no devices:
  Ask user to verify socket, data cable and Safe Mode; inspect the exact DFU driver
  before considering WinUSB. Serial COM detection is not coprocessor DFU detection.
Mic is silent despite normal ESP32 boot:
  Read coprocessor version and 48 kHz role pairing first, then real capture.
Wake model loaded but no wake:
  Match model header name with set-wake selector; use real speech and policy-aware
  rolling scores. Do not confuse a forced wake test with acoustic acceptance.
Gateway duplication or ports already occupied:
  Inventory process executable/command line, creation time and listener owner
  read-only. Do not kill all Python processes. Follow main's ownership policy.
NAS unavailable in task:
  Use local assets. A user-mapped drive may not exist under task/elevated logon.

Delayed OLD completion messages / stale tool notifications:
- A background completion notification can arrive after a later command has
  already succeeded, or after main has changed service state. Its arrival time
  is NOT the execution time or current status. Check the exact command/session,
  start time, exit code and artifact path before acting on it.
- Do not rerun a flash, installer, restore or service launch solely because an old
  message mentions failure/incomplete work. Read fresh narrowly scoped state.
- Distinguish an old agent/build completion notification from stale spoken audio:
  for spoken replies, correlate current turn/session/request IDs and timestamps,
  then check duplicate runtime/announcement producers. Avoid reading/exporting
  personal session history to diagnose a generic startup issue.
- Keep build logs, service logs and hardware validation separate. A background
  installer exit 0 cannot establish current device connectivity or current voice.
- On true uncertainty stop and report the last independently verified stage;
  never replace missing evidence with plausible-looking success output.

14. ROLLBACK AND BACKUP DISCIPLINE
================================
Always capture the current state privately before rollback so rollback is itself
reversible. Do not overwrite the pre-install backup. Verify the selected backup's
hash and fitted flash size, not just its filename.

Project rollback: restore the previously reviewed bootloader/table/application
REGIONS as a compatible set, preserving NVS/TLS/model where layout allows. If
credentials/configuration changed, coordinate restoring their private paired
state; never overwrite current CA/device registry with an arbitrary old copy.

True vendor reset is the exceptional case where a full 8 MB write at 0x0 is
appropriate. After approval and backup, select the stock ESP32 image from section
5 and compare its hash, write it whole at 0x0, read back 8388608 bytes and compare
again. This removes the project application/state and should stop registry use.
Separately restore the coprocessor via the SAME user Safe Mode + WinUSB/DFU steps
but choose xmos-official-v1.0.4-dfu.bin. Verify that image's hash first. Restoring
only one chip does not establish true factory compatibility; stock ESP32 plus
48 kHz-master coprocessor compatibility was not proven by this documentation.

Host rollback: follow section 12 ownership/stop controls; disable only this
project's scheduled task and stop only its owned children. Restore selected
project patches/config from private backups after comparing version compatibility.
Do not remove unrelated Hermes startup or kill unrelated Hermes/Python processes.
Do not rotate/revoke/regenerate keys as an undocumented side effect of rollback.
